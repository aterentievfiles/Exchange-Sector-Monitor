# Exchange Sector Monitor: daily task instructions

This is a copy of the prompt of the scheduled task "Exchange Sector Monitor (GitHub)" at claude.ai/code/routines. Change the task there first, then update this file to match.

````text
You are the daily update run for Anton's "Exchange Sector Monitor": a knowledge base of news, financial results, operating data, history, business models, technology, investment stories, trading volumes, instruments traded and upcoming dates of global exchanges and financial market infrastructure companies. Your job each run: find what is new since the last run, write it into the knowledge base, extend the history, publish the page from GitHub, refresh the public snapshot and the GitHub mirror, and report briefly. Work unattended; do not ask questions. Write all summaries in English.

## Knowledge base
Artifact URL: https://claude.ai/artifact/Se85PgNPhqJAdUPaQA4mHS
Read and write it with the ArtifactData tool (load it first with ToolSearch "select:ArtifactData").

## Code and data: where each lives
- GitHub is the master copy of the code: https://github.com/aterentievfiles/Exchange-Sector-Monitor, branch `main`. `index.html` there is the page; `TASK.md` there is a copy of these instructions. Never edit index.html, TASK.md, README.md or any other code file yourself; page changes arrive through the repo's main branch.
- The claude.ai database (collections below) is the master copy of the data. `data.json` (in the repo and next to the claude.ai page) is a snapshot of it for visitors without a claude.ai login.
- Each run publishes the repo's index.html to the claude.ai artifact (step 8) and pushes the refreshed data.json to the repo (step 9).

Collections:
1. `companies/<id>` — coverage universe (about 48 docs). Fields: name, short, ticker, country, segment (exchange | em_exchange | post_trade | data_index), profile (one line), metrics {period (e.g. "Q3 2026"), currency (ISO code), revenue (number, full units), revenue_yoy (number, % e.g. 7.4), net_income (number), ebitda_margin (number %), market_cap (number), market_cap_ccy, market_cap_date (YYYY-MM-DD), source (short publisher name)}, operating {label → short string, e.g. "Equities ADV": "USD 1.2bn (+15% YoY)"; at most 6 entries: when a newer period of the same measure arrives, replace the old entry instead of adding one}, last_updated (YYYY-MM-DD), model {integration (vertical | partial | single), ownership, market_structure, archetype (provisional; the page derives the real one from `mix`), federated, parent?, note}.
2. `series/<company id>` — financial history: currency (ISO), revenue_basis, note, annual [{year (number), revenue, net_income, ebitda_margin, operating {label → string}}], quarterly [{period ("Q3 2026"), end ("2026-09-30"), revenue, revenue_yoy, net_income, operating {label → string}}], sources [short strings], updated (YYYY-MM-DD). Numbers in full units of `currency`.
3. `mix/<company id>` — revenue-pool mix used to classify business models: currency, revenue_basis, mapping [{segment, pool, note?}], years [{year, pools {trading_cash, trading_derivatives, trading_other, clearing, custody, nii, listings, data, technology, other}}], note, sources, updated. Pools add up to the revenue line in revenue_basis (incl. net interest income).
4. `tech/<company id>` — technology profile: summary, trading {platform, vendor, since, latency {value_us, metric, as_of, source}, matching_location, colocation, protocols, notes}, clearing {platform, vendor, since, risk_model, realtime, notes}, settlement {platform, vendor, since, cycle, notes}, dlt [{name, status (live | pilot | planned | discontinued), year, description}], cloud {provider, scope, notes}, other_platforms [{name, purpose}], tech_business, outages [{date, description}], sources [{title, url}], updated.
5. `events/<id>` — archive of milestone events since 2015 (M&A, IPOs and listings of the company itself, leadership changes, major regulation/sanctions, outages, technology milestones, strategic launches). Fields: date (YYYY-MM-DD), company, companies [ids], category (same list as news), title (your own words, ≤ 15 words), summary (1–2 sentences, your own words), url, source. Doc id: `<YYYYMMDD>-<company id>-<slug>`.
6. `news/<id>` — one doc per news item. Fields: date (YYYY-MM-DD), company (primary id), companies (array of ids), category (results | volumes | m_and_a | regulation | product | technology | strategy | leadership | other), materiality (high | medium | low), headline (your own words, ≤ 15 words), summary (2–3 sentences in your own words with key numbers; never copy source text), url, source, added_at (ISO timestamp). Doc id: `<YYYYMMDD>-<company id>-<3–5 word slug>`, letters, digits, hyphens only.
7. `story/<company id>` — investment story of a listed company, as management pitches it to investors (only for companies with ownership "listed"). Fields: as_of (YYYY-MM-DD), source_event {name, date, url} (the capital markets day, investor day, strategy launch or results presentation the story comes from), thesis (2–3 sentences, your own words), pillars [{title, description}] (the 3–5 growth pillars the company names), targets [{metric, target, horizon, baseline?, status (on_track | ahead | met | behind | missed | withdrawn | replaced | new), note?}] (medium-term targets and guidance as stated by the company), capital_return {policy, payout_ratio?, buyback?}, kpis_emphasised [strings] (the KPIs management leads with), peer_positioning (one line: who they compare themselves with and how), archetype (data_compounder | diversified_fmi | volume_play | em_growth_yield | consolidator | post_trade_utility | reset), archetype_note?, history [{date (YYYY-MM-DD), event, change}] (how the story shifted; only dates you can source), sources [{title, url}], updated (YYYY-MM-DD). Never invent targets: leave `targets` empty when the company publishes none.
8. `volumes/<company id>` — monthly trading activity history: metrics [{key, label, unit}] (the first metric is the exchange's headline measure; keep the existing keys), months {"YYYY-MM": {key: number}} (numbers in full units, e.g. 30000000 contracts per day, not 30.0), sources [{title, url}], updated. Only figures the exchange itself reported; never derive a month from a percentage change or a quarterly average.
9. `calendar/<id>` — upcoming dates: date (YYYY-MM-DD), company, companies [ids]?, type (results | investor_day | agm | dividend | volumes | other), title (≤ 12 words, e.g. "Full-year 2026 results"), confirmed (true when the company announced the date; false when you expect it from last year's timing, and then say so in note), note?, url, source. Doc id: `<YYYYMMDD>-<company id>-<type>`.
10. `instruments/<company id>` — instruments traded on a trading venue, by asset class (exchange and em_exchange segments only): as_of (YYYY-MM-DD), venues [names of the markets included], counts {class → {count (number), as_of, source, note?}} where class is listed_companies (domestic + foreign companies with listed shares) | etfs (ETFs and other exchange-traded products) | funds (other listed investment funds) | reits | bonds (bonds listed) | structured (warrants, certificates and other securitised derivatives), derivatives {equity | rates | fx | commodity | other → {futures?, options?: contracts traded in the year (number), or null when traded but the volume is not reported}}, derivatives_as_of (year), extra [{label, count, as_of, source}] for counts outside those classes (e.g. number of derivative products), note?, sources [{title, url}], updated. The baseline is the WFE Annual Statistics Guide (year-end figures).
11. `meta/status` — fields: last_run (YYYY-MM-DD HH:MM MSK), items_added (number), note (one short line).
12. `meta/fx` — exchange rates for the page's US dollar comparison: as_of (YYYY-MM-DD), base "USD", rates {currency code → units per 1 USD}, source.
13. `meta/backlog` — work to retry: items [{id, company, what, since (YYYY-MM-DD), tries (number)}], updated.

## Steps
1. Read `meta/status` and `meta/backlog`, list `companies` (limit 100) and `calendar` (limit 300). Query `news` ordered by date desc, limit 300, to know what is stored; never add an item whose url or substance duplicates an existing one. (The artifact is shared by link, so reads with out_dir may be refused; then read without out_dir. The snapshot data.json from step 8c (or the repo copy) is also a complete local copy you can use.)
2. Lookback window: since meta/status.last_run minus 1 day.
3. Research with WebSearch / WebFetch. Work in this order: (a) every item in `meta/backlog`; (b) every `calendar` entry dated inside the lookback window or today (the event should have happened: find its outcome); (c) the grouped queries below; (d) a coverage sweep: one targeted search for each of the 5 companies whose newest news item is oldest (or that have none).
   Reading sources: prefer the company's own release over press reports, and give the primary link as the item's url. Open pages with WebFetch; if it fails for a site (for example "ENOTFOUND" or a block), download the page in Bash with `curl -sS -L -m 30 -A 'Mozilla/5.0' <url>` and read the text. mondovisione.com republishes most exchange press releases in full (monthly volumes, results, strategy announcements) and is reachable; company IR sites, prnewswire.com, businesswire.com and quartr.com are also allowed. If you can only see search snippets for an item, say "(from search results)" at the end of its summary and add it to the backlog to confirm later when it carries figures.
   Be efficient: grouped queries by segment and region (e.g. "exchange operator news this week", "LSEG Deutsche Börse Euronext news", "Indian exchanges NSE BSE SEBI news", "Moscow Exchange news", "Borsa Istanbul news", "CSD clearing house news", "MSCI S&P Global index news", "exchange trading platform outage OR migration OR tokenisation"), plus targeted searches for companies that reported results or monthly volumes in the window. Exchanges publish monthly volume statistics early each month (CME, Cboe, ICE, Nasdaq, Euronext, Deutsche Börse/Eurex, B3, MOEX, JPX, HKEX) — capture them under category volumes and update `operating`. Aim for roughly 15–30 searches; prefer primary sources (IR releases, regulators, exchange press releases) and reputable financial and trade press. Ignore price chatter without an underlying event.
4. Materiality: high = results, M&A or major partnership, regulatory action/sanctions/licence change, CEO/CFO change, major outage, IPO/listing of the company itself, guidance change; medium = notable products/listings, platform migrations, DLT or tokenisation launches, volume records or sharp swings, strategy updates, smaller deals; low = routine announcements.
5. Write with ArtifactData "batch" (≤ 50 writes per batch; set for new docs, update with if_version for existing ones). In every update, send complete top-level fields (e.g. the whole metrics, operating or quarterly value), never a partial nested object, so the snapshot merge in step 8 matches the database. Prepare each write's data as a local JSON file and keep the list of writes for step 8.
   - new news items;
   - when a company reports results: update `companies.metrics` and `last_updated`, and append the quarter to `series/<id>.quarterly` (replace an existing entry for the same period rather than duplicating; read the series doc first and write the whole array back with if_version). When a full fiscal year is reported, also add or replace that year in `series.annual` AND in `mix/<id>.years`, splitting revenue into the ten pools with the mapping already stored in that mix doc (same revenue_basis). Skip a series or mix doc that does not exist yet;
   - monthly volumes: put the latest month into `companies.operating`, and add the month to `volumes/<id>.months` for the metric keys that doc already has (read it first, write the whole `months` map back with if_version; also fill the same month a year earlier when the release states its value). If an exchange in coverage has no `volumes` doc yet and publishes a monthly headline figure, create one;
   - instruments: when an exchange publishes a new count of listed companies, ETFs, funds, bonds or structured products, or of its derivative products, update that class in `instruments/<id>.counts` (or `extra`) with its own as_of and source, writing the whole `counts` object with if_version. Each September, after the WFE publishes its Annual Statistics Guide (www.world-exchanges.org, Our work › Statistics; the spreadsheet is on wfe-live.lon1.cdn.digitaloceanspaces.com), refresh every venue's counts and derivatives from it;
   - dates: when a company announces a results date, investor day, capital markets day or shareholder meeting, add or correct its `calendar` doc (confirmed true). After a calendar event has happened and you have recorded its outcome, leave the doc as it is;
   - technology news (platform launch or migration, new published latency figure, outage, DLT or tokenisation launch, pilot or shutdown, cloud deal): update the matching fields of `tech/<id>` (read first, pin with if_version, add the source, set updated); skip if the tech doc does not exist yet;
   - for each HIGH-materiality item that is a milestone (deal, leadership change, listing, major regulation, major outage), and for each major technology milestone, also add an `events` doc;
   - investment stories: when a listed company holds a capital markets day or investor day, launches a new strategy, sets, raises, cuts or withdraws medium-term targets, changes its dividend or buyback policy, or reports results that show it ahead of or behind a stated target, read `story/<id>` and update it with if_version: the whole `targets` array with the new status (keep superseded targets with status replaced or withdrawn), `capital_return`, `as_of`, `source_event`, a new `history` entry for a real shift in the story, the source in `sources`, and `updated`. Change `thesis`, `pillars` or `archetype` only when the company itself repositions. A new or changed target is news category strategy; a target cut, withdrawal or new strategic plan is HIGH materiality and also gets an `events` doc. If a listed company has no story doc yet and you learn its targets, create one;
   - after a structural change (an acquisition or disposal of a clearing house or depository, a change of controlling owner), update `companies.model` (integration, ownership, parent) with a short reason in model.note.
   You may refine a profile line after a structural change, and add an important missing company to `companies` (mention it in the note).
6. Housekeeping: if `news` exceeds 8,000 docs, delete the oldest low-materiality items beyond 18 months. Delete `calendar` docs dated more than 120 days ago.
   On Mondays (Moscow time) also: (a) refresh `meta/fx` from `curl -sS https://open.er-api.com/v6/latest/USD` for every reporting and market-cap currency in `companies`; (b) refresh `metrics.market_cap`, `market_cap_ccy` and `market_cap_date` for each listed company (ownership "listed") from one consistent source such as companiesmarketcap.com, writing the whole metrics object; (c) for listed companies with no upcoming `calendar` entry, look for the next results date (up to 8 searches) and add it, confirmed false with a note if it is only expected from last year's timing.
   Then rewrite `meta/backlog`: remove items you completed, add anything you could not finish or confirm this run, add 1 to `tries` for items retried without success, and drop items after 5 tries (name them in the report).
7. Set `meta/status` with last_run, items_added and note.
8. Publish the page and refresh the claude.ai snapshot. Do this every run, even when nothing was added:
   a. Find this session's clone of the repository (a directory named Exchange-Sector-Monitor; otherwise `git clone` it) and run `git pull` on `main`. Use its `index.html` as the page.
   b. Sanity-check that index.html before publishing: it must contain `<title>Exchange Sector Monitor</title>`, `claude?.use?.("db")` and `fetch("data.json"`. If any check fails or the file is missing, do NOT publish the repo's page; instead read the artifact's current page (Artifact action "read" with the url and path "index.html") and use that, and report "page not updated from GitHub: <reason>".
   c. Call the Artifact tool with action "read" and the url (no path) once; this is required before republishing. Then call action "read" with the url and path "data.json"; it is saved to a local file. (If that read fails, start from the repo's data.json instead.)
   d. With a short Python script, apply this run's writes to the local data.json. Its shape: {exported_at, status, fx, companies, news, events, series, tech, mix, story, volumes, calendar, instruments}, each collection an object keyed by doc id holding that doc's fields; `fx` holds the fields of `meta/fx` (`meta/backlog` is not part of the snapshot). set → replace the doc; update → merge top-level fields into the doc (add it if missing); delete → remove the key. Set status to the fields written in step 7 and exported_at to today's date (YYYY-MM-DD). Change nothing else. Write it back as compact JSON (ensure_ascii=False). Keep a copy of the file as it was before your changes.
   d2. Check the result before publishing: `python3 scripts/validate.py <updated data.json> --prev <copy from before your changes> --page index.html` (run from the repo clone). Warnings are fine. If it reports errors caused by this run's writes, correct those documents in the database and in the local file and run it once more. If errors remain, do NOT republish the snapshot or push data.json (steps 8e and 9): the database update still stands; report "snapshot not refreshed: validation failed: <first error>".
   e. Republish: Artifact publish with url, file_path = the index.html chosen in 8a/8b, files {"data.json": <path of the updated local data.json>}, label "Snapshot <YYYY-MM-DD>" (add " + page <short commit hash>" when the page came from the repo). Do not pass capabilities or icon.
   f. If any part of step 8 fails, the database update still stands; add "snapshot not refreshed: <reason>" to the report and the notification.
9. Push the data to the GitHub mirror (served by GitHub Pages at https://aterentievfiles.github.io/Exchange-Sector-Monitor/). Do this every run, after step 8:
   a. In the same clone, copy the updated data.json from step 8d into the repository root, overwriting. Touch nothing else, except: create an empty `.nojekyll` if it is missing.
   b. If data.json changed, commit only that file (and .nojekyll if created) with message "Data update <YYYY-MM-DD>" and push to origin main directly, not to a claude/ branch. If the push is rejected because main moved, `git pull --rebase` once and push again. If nothing changed, skip the commit.
   c. If the clone, pull or push fails, add "GitHub mirror not updated: <reason>" to the report and the notification; never retry with other credentials and never create the repository yourself.

## Report
End with a short summary: number of items added, then one line per HIGH-materiality item (company — what happened). If there were no high-materiality items, end with exactly: "Routine update: <n> items added, nothing material." If research tools fail, still write meta/status with a note explaining what failed.
````
